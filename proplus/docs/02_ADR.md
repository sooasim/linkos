## ADR-001 모듈형 모놀리스로 시작한다

**상태** 채택 (2026-10-22)

**맥락**
MVP 범위가 12개 모듈(M01~M12)이고 그중 하나(`proof`)만 트래픽·운영 특성이 다르다.
검증 운영 비용과 수동 검토 큐의 처리량은 아직 측정되지 않았다(전략 §11-2).
팀은 작고, 같은 서버에서 LINKOS 가 이미 운영 중이다.

**결정**
Next.js 16 server layer 하나가 화면과 `/api/v1/*` 를 모두 서비스하고, 비동기 작업만 별도 워커 프로세스로 돌린다.
모듈 경계는 네트워크가 아니라 **디렉터리(`services/api/src/modules/*.ts`)와 import 방향**으로만 강제한다.
모듈은 자기 테이블에만 쓰고, 다른 모듈의 데이터는 읽기로만 접근한다.

**근거**
- 기술백서 §2 가 권고하는 배치가 "모듈형 모놀리스 + 비동기 작업 큐"다.
- 기술백서 §4 는 웹/API 프레임워크를 "하나를 기준으로 선택, 중복 서버 방지"로 못 박았다.
- 같은 배치가 LINKOS 에서 운영 중이다 → systemd unit · nginx vhost · 배포 스크립트 형태를 그대로 복제할 수 있고 운영 부담이 늘지 않는다.

**결과**
- 단일 트랜잭션에서 도메인 쓰기 + `outbox_events` 기록이 가능하다 (기술백서 §7 요구).
- `proof` 를 나중에 떼어낼 수 있도록 import 방향을 전략 §3 에서 고정했다: `proof` 는 `identity` 외의 모듈을 import 하지 않는다.
  특히 `proof → billing` 역방향 의존이 생기면 N-2(배지 유료 구매 금지)가 구조적으로 깨진다.
- 모듈 경계가 컴파일러로 강제되지 않으므로 코드리뷰 항목으로 남는다(이 비용을 감수한다).

**대안과 기각 이유**
- *Next.js + NestJS 2 프로세스*: 기술백서 §4 의 "중복 서버 방지"와 충돌하고, LINKOS 배포 스크립트를 재사용할 수 없다.
- *처음부터 서비스 분리*: 검증 상태 변경 → 감사로그 → outbox 가 한 트랜잭션에 들어가야 하는데(N-6, N-183) 분산 트랜잭션이 필요해진다. 측정되지 않은 부하를 위해 일관성을 포기하는 거래다.

## ADR-002 공개 API 는 allowlist 필드만 반환한다

**상태** 채택 (2026-10-22)

**맥락**
데이터모델 §3 이 공개/비공개 필드를 목록으로 나눠 두었다. 이 목록을 주석이나 블랙리스트로 표현하면
컬럼이 추가될 때마다 **조용히 유출**된다 — 아무도 블랙리스트에 새 컬럼을 추가하지 않는다.

**결정**
공개 응답은 원본 행을 가공하지 않고 `packages/domain/src/publicDto.ts` 의 필드 allowlist로 **새 객체를 재구성**한다.
allowlist 밖 키는 런타임에 사라진다. 그 위에 DB 계층의 `public_profile_view` / `public_badge_view` /
`public_metric_view` / `public_offer_view` 를 한 겹 더 둔다. 공개 조회 경로는 이 뷰만 읽는다.

**근거**
- 기술백서 §10 ADR 초기 목록 / 데이터모델 §3.
- 보안정책 §2 의 위협 "IDOR·과공개"는 응답 조립 단계에서 막는 것이 가장 싸다.
- 전략 §2 N-4.

**결과**
- 새 공개 필드를 노출하려면 **뷰와 allowlist 두 곳**을 고쳐야 한다. 이 마찰은 의도된 것이다.
- `assertNoPrivateKeys()` 가 응답 객체를 재귀 검사하므로, 중첩 객체에 실수로 끼어든 `email`·`token` 류 키를 테스트가 잡는다.
- 공개 응답에 디버그 정보를 끼워 넣는 임시 코드가 불가능하다.

**대안과 기각 이유**
- *블랙리스트(민감 키 제거)*: 추가되는 컬럼이 기본 공개가 되는 구조다. 기각.
- *ORM serializer group*: ADR-007 로 ORM 자체를 쓰지 않는다. 또한 직렬화 애너테이션은 뷰 수준 강제를 주지 못한다.

## ADR-003 신뢰 배지는 검증 상태와 출처를 표시하고 단일 점수는 MVP 에서 제외한다

**상태** 채택 (2026-10-22)

**맥락**
"믿을 수 있는 사람"을 숫자 하나로 요약해 달라는 요구는 반드시 나온다(전략 §11-3).
그러나 단일 점수는 (a) 이의제기 때 설명할 수 없고, (b) 역산되면 점수 최적화 행동을 유발하며,
(c) 가중치 변경이 사용자 입장에서 소급 불이익이 된다.

**결정**
신뢰를 표현하는 유일한 단위는 **배지**이고, 배지는 `(라벨, 검증 강도, 범위, 검증일, 만료일, 발급기관)`
6개 값을 항상 함께 내보낸다. 하나라도 비면 배지를 숨긴다. 집계 점수 컬럼도, 점수 기반 정렬키도 만들지 않는다.
프로필 완성도(`completeness`)는 워크스페이스 안내 전용이고 공개 DTO 에서 제외한다.

**근거**
- 기술백서 §10 ADR-003 / 기획서 §13.
- 보안정책 §4.1 검증 강도 4단계, §4.8 수치 표기 의무, §4.9 비교 표현 제한.
- 브랜드 §5 배지 카피 규칙(상태와 출처를 함께 말한다).

**결과**
- 검색 랭킹은 점수가 아니라 재현 가능한 근거 코드(`badge_present`, `specialty_match` …)로만 설명된다 (N-15, ADR-005).
- 비교 수요가 확인되면 점수가 아니라 "같은 직군 내 지표 분포"로 답한다 (보안정책 §4.9).
- UI 는 색만으로 상태를 말할 수 없다 — 색 + 텍스트 + 아이콘을 함께 쓴다(브랜드 §7, 접근성).

**대안과 기각 이유**
- *가중 신뢰점수(0~100)*: 설명 가능성·이의제기 가능성을 둘 다 잃는다. 제품 차별화의 핵심을 버리는 선택이다.
- *배지 개수 기반 정렬*: 점수의 우회 구현이다. 배지를 많이 받는 행동을 최적화하게 만든다.

## ADR-004 증거 원본과 공개 배지 데이터를 분리 저장한다

**상태** 채택 (2026-10-22)

**맥락**
증빙 파일에는 신분증·계약서·급여명세 같은 **공개될 일이 절대 없는 원본**이 들어온다(보안정책 §2 "증빙 파일 유출").
같은 테이블에 공개 라벨과 원본 경로가 함께 있으면 `SELECT *` 한 번으로 사고가 난다.

**결정**
- `evidence` / `evidence_files` / `verifications` / `verification_notes`: 내부 전용. 파일은 저장 암호화 + 단기(60초) signed URL, 다운로드마다 `audit_logs`.
- `badges`: 공개 라벨 전용. **`evidence` 를 참조하지 않고 `verification_id` 만 가리킨다.**
- 공개 조회 경로(`public_*_view`)에는 `evidence_files` 조인이 존재하지 않는다.

**근거**
- 기술백서 §10 ADR-004 / 데이터모델 §3 공개·비공개 구분.
- 보안정책 §4.3(증빙 보관·접근), §2(최소권한·감사).
- 전략 §2 N-5.

**결과**
- "검증 완료 후 원본 삭제, 검증 이력 보존" 기본값이 가능해진다(데이터모델 §7-2). 배지는 원본 없이도 유효하다.
- 공개 응답에 증거가 섞일 **경로 자체가 없음**을 스키마가 증명한다 — 리뷰가 코드 읽기에 의존하지 않는다.
- 배지 발급은 `badges_require_verified` 트리거를 통과해야 한다: `verified` + `method <> 'self_declared'` (N-1 보강).

**대안과 기각 이유**
- *한 테이블 + 컬럼 단위 권한*: 뷰·쿼리 한 곳만 틀려도 원본이 나간다. 사고의 비용이 비대칭이다.
- *파일을 DB 바이트로 저장*: 백업에 원본이 영구히 섞이고 보존기간 삭제(데이터모델 §6)를 수행할 수 없다.

## ADR-005 검색 인덱스는 파생 데이터이며 원본 DB 가 진실의 원천이다

**상태** 채택 (2026-10-22)

**맥락**
검색 엔진은 운영 중 교체·재구축·유실될 수 있다. 인덱스가 사실의 원천이 되면 유실이 데이터 손실이 되고,
인덱스에 비공개 필드를 넣어 두면 필터 실수 한 번이 유출이 된다(보안정책 §2 "검색 인덱스 PII").

**결정**
인덱싱 입력은 **`public_profile_view` 뿐**이다. 인덱스는 언제든 `DROP` 하고 재색인해도 되는 캐시로 취급한다.
권한 판정·사실 조회는 인덱스가 아니라 원본 DB 에서 한다. 인덱스에만 존재하는 값은 두지 않는다.

**근거**
- 기술백서 §10 ADR-005, 모듈명세 M11.
- 보안정책 §2 의 통제 위치 표: "검색 인덱스 PII → 인덱싱 입력이 `public_profile_view` 뿐".

**결과**
- 검색 백엔드를 어댑터(`services/api/src/lib/searchIndex.ts`)로 교체할 수 있다 (ADR-006).
- 비공개 필드가 색인될 경로가 없다 — 필터 버그가 유출이 되지 않는다.
- 색인 지연이 생기면 "결과가 늦게 뜬다"로 끝난다. 틀린 권한 판정으로 번지지 않는다.

**대안과 기각 이유**
- *전체 필드 색인 + 질의 시 필터*: 필터 한 줄의 실수가 곧 유출이다. 또한 색인 백업이 PII 백업이 된다.
- *검색 엔진을 사실의 원천으로*: 재구축 불가능한 상태가 생기고, 트랜잭션·감사로그와 일관성을 맞출 수 없다.

## ADR-006 오픈소스는 라이선스/보안/유지보수 검토 후 선택한다

**상태** 채택 (2026-10-22)

**맥락**
오픈소스검토 §4 는 도입 전 체크리스트(현재 LICENSE 원문 확인 · SPDX · 커밋 해시 고정 · CVE 조회 ·
의존성 스캔 · SBOM · 법률검토 기록)를 요구한다. 2026-10-22 기준 **하나도 완료되지 않았다.**

**결정**
이번 구현은 후보 오픈소스 프로젝트를 코드에 넣지 않는다. 대신 **교체 지점을 어댑터로 비워 두고 폴백을 직접 구현**한다.

| 후보 | 어댑터 위치 | 실사 전 폴백 |
|---|---|---|
| Meilisearch | `services/api/src/lib/searchIndex.ts` | Postgres `tsvector` + `pg_trgm` |
| Umami | `services/api/src/modules/analytics.ts` | 자체 `analytics_events` 집계 |
| Cal.com | `services/api/src/modules/booking.ts` | 자체 `availability_rules` + `appointments` |
| Chatwoot | `outbox_events` 소비자 | 리드 inbox |
| walt.id / EAS | `packages/domain/src/credential.ts` | 내부 발급 배지만 |
| Medusa | `services/api/src/modules/catalog.ts` | 외부 링크형 상품 카드 |

**근거**
- 오픈소스검토 §3 "실제 주문까지 필요한 경우에만 POC", §4 체크리스트, §5 권고.
- 특히 오픈소스검토 §5: **"검증 배지의 신뢰 정책을 외부 프로젝트에 맡기지 않는다."**

**결과**
- 폴백 구현 비용이 발생한다(검색·예약·분석). 이것을 받아들이는 대가로 라이선스·공급망 리스크를 0 으로 둔다.
- 실사가 끝나면 어댑터 구현만 추가하면 된다 — 호출부는 바뀌지 않는다.
- 신뢰 정책(검증 강도 게이트·배지 발급 조건)은 어떤 경우에도 `packages/domain` 안에 남는다.

**대안과 기각 이유**
- *지금 Meilisearch/Cal.com 도입*: SPDX·SBOM·법률검토 기록이 없는 상태로 운영에 들어가면 나중에 제거 비용이 더 크다.
- *상용 SaaS 로 대체*: 증거 원본·리드 PII 를 외부로 보내는 결정이 되고, 데이터모델 §6 보존기간·국외이전 미결정 항목을 침범한다.

## ADR-007 ORM 을 쓰지 않고 생 SQL 로 간다

**상태** 채택 (2026-10-22)

**맥락**
기술백서 §4 는 ORM 후보로 Prisma/Drizzle 을 제시하면서 "하나를 선택"을 요구한다(둘을 섞지 말라는 뜻).
그런데 이 제품의 핵심 안전장치는 **뷰와 트리거와 CHECK 제약**이다 — `badges_require_verified`,
`audit_logs_append_only`, `metric_claims_require_integration`, `appointments_no_overlap`,
`public_*_view` 4개. 전부 ORM 스키마 언어로 표현되지 않는 것들이다.

**결정**
`pg` 드라이버 + 직접 SQL 로 간다. 마이그레이션은 `proplus/db/migrations/*.sql` 번호 순서 파일이고,
러너(`services/api/src/migrate.ts`)가 advisory lock 으로 동시 실행을 막는다.
쿼리는 모듈 계층(`services/api/src/modules/*.ts`)에만 둔다.

**근거**
- 전략 §6 기술 선택표(ORM: 없음).
- 공개/비공개 경계를 ADR-002·ADR-004 처럼 **DB 객체로 강제**하는 설계에서, ORM 추상화는 그 객체를 숨기고 우회하게 만든다.
- LINKOS 가 같은 저장소에서 19개 마이그레이션을 직접 SQL 로 운영 중이다 — 검증된 패턴이고 러너 코드를 복제할 수 있다.

**결과**
- 타입 안전은 ORM 이 아니라 **모듈 경계의 반환 타입**과 통합테스트가 책임진다. 모듈 함수는 명시적 인터페이스를 반환한다.
- SQL injection 은 파라미터 바인딩(`$1`)으로만 막는다. 문자열 연결로 쿼리를 만드는 코드는 리뷰에서 거부한다.
- 스키마 변경은 사람이 읽는 SQL diff 로 남는다 — 트리거·뷰 변경이 리뷰에 드러난다.

**대안과 기각 이유**
- *Prisma*: 뷰·트리거를 1급으로 다루지 못해 `$queryRaw` 가 섞인다. "ORM 하나만" 요구를 형식적으로만 만족하고 실제로는 두 가지 접근이 공존한다.
- *Drizzle*: SQL 에 가깝지만 마이그레이션 생성기가 트리거·뷰를 관리하지 않아 결국 수동 SQL 파일을 함께 써야 한다. 두 소스를 유지할 이유가 없다.

## ADR-008 큐는 Redis 가 아니라 Postgres outbox 다

**상태** 채택 (2026-10-22)

**맥락**
기술백서 §7 이 비동기 처리에 요구하는 것은 두 가지다: **(1) 외부 연동을 유발하는 쓰기는 같은 트랜잭션에 기록**,
**(2) 소비자는 idempotent**. 전달 지연 수십 초는 요구사항에 없다(알림·색인·메일 발송).

**결정**
`outbox_events` 테이블 + 워커 폴링(`services/api/src/worker.ts`)으로 간다. Redis/BullMQ 를 도입하지 않는다.
도메인 쓰기와 이벤트 적재는 **같은 트랜잭션 client** 를 쓴다 — `enqueue(client, envelope)` 는 풀이 아니라
트랜잭션 client 를 인자로 받는 시그니처로 그 규칙을 강제한다.

**근거**
- 전략 §6 기술 선택표(Queue: Postgres outbox + 워커 폴링).
- 기술백서 §7. Redis 를 끼우면 "같은 트랜잭션" 요구를 만족할 수 없어 2-phase 또는 중복 전송 보정이 필요해진다 —
  outbox 패턴이 존재하는 이유 자체다.
- 운영 측면: 백업·복구 대상이 Postgres 하나로 끝난다. 큐 유실과 DB 복원 시점이 어긋나는 사고가 없다.

**결과**
- 폴링 간격만큼 지연이 생긴다(기본 수 초). 사용자 대기 경로에 outbox 를 두지 않는다.
- `processed_at` / `attempts` / `next_attempt_at` 로 재시도·백오프를 DB 안에서 관찰할 수 있다. 실패 적체가 운영 지표가 된다.
- 처리량 병목이 **측정되면** 그때 BullMQ 로 옮긴다. 소비자가 이미 idempotent 하므로 옮기는 비용은 낮다.

**대안과 기각 이유**
- *Redis + BullMQ 지금 도입*: 트랜잭션 원자성을 잃고, 운영 구성요소와 실사 대상 의존성이 하나 늘어난다(ADR-006).
- *`LISTEN/NOTIFY` 만 사용*: 알림은 전달 보장이 없어 유실 시 복구 경로가 없다. outbox 테이블은 유지하고 지연 단축용으로만 나중에 얹을 수 있다.

## ADR-009 LINKOS 와 DB·프로세스·기능원장을 분리하고 `P-xxx` 네임스페이스를 쓴다

**상태** 채택 (2026-10-22)

**맥락**
PROPLUS 는 LINKOS 와 같은 저장소·같은 서버에서 개발·운영된다. 그러나 두 제품의 신뢰 모델은 반대 방향이다:
LINKOS 는 관계 강도를 **추정**하고, PROPLUS 는 추정을 **금지**한다(자기기재는 배지 불가 — 보안정책 §4.2).
또한 루트 `CLAUDE.md` §1 은 LINKOS 197개 `F-xxx` 를 삭제·통합·이름변경 금지로 묶어 두었다.

**결정**
저장소는 공유하고 **그 밖의 모든 것을 분리**한다.

| 항목 | 값 |
|---|---|
| 기능원장 | `proplus/docs/01_FEATURE_REGISTRY.yaml`, 네임스페이스 `P-xxx` |
| 데이터베이스 | `proplus` (LINKOS 는 `linkos`) |
| 마이그레이션 | `proplus/db/migrations/`, advisory lock `727275` (LINKOS 는 `727274`) |
| 세션 쿠키 | `pp_session` / `pp_anon` (LINKOS 는 `lk_*`) |
| 프로세스 | `proplus-web.service` :4400 · `proplus-worker.service` |
| 도메인 패키지 | `@proplus/domain` (LINKOS `@linkos/domain` 과 교차 import 금지) |
| 스토리지·감사로그·환경변수 | 전부 별도 |

공유하는 것은 pnpm 워크스페이스, `tsconfig.base.json`, Playwright 러너, CI 러너, 배포 서버, 그리고 **검증된 코드 패턴**뿐이다.

**근거**
- 전략 §1 분리 근거 3가지(기능 ID 충돌 금지 · 반대 방향 신뢰 모델 · 배포 격리).
- 기능 ID: `N-xxx`(인적네트워크 번들)가 같은 이유로 이미 별도 네임스페이스를 쓰는 전례가 있다(루트 `CLAUDE.md` §1).
- 신뢰 경계: 검증 콘솔과 증거 원본 스토리지는 LINKOS 와 다른 경계다(보안정책 §2 관리자 오남용).

**결과**
- 한쪽 사고가 다른 쪽 데이터에 닿지 않는다. 증거 원본 유출 반경이 PROPLUS 로 한정된다.
- 두 제품의 마이그레이션·배포를 서로 기다리지 않는다.
- 코드 재사용은 복사로 한다(db 헬퍼·route 래퍼·migrate 러너). **중복을 감수하고 결합을 피하는 거래**다 —
  공용 패키지로 묶으면 한쪽 제품 요구가 다른 쪽 신뢰 정책을 바꾸게 된다.
- 추적성 스크립트도 분리한다: `pnpm traceability`(LINKOS) / `pnpm proplus:traceability`(PROPLUS).

**대안과 기각 이유**
- *단일 DB 에 스키마 분리*: 롤 권한·백업·보존기간·감사로그가 섞인다. 특히 `audit_logs` append-only 권한 모델을 두 제품이 공유하게 된다.
- *`F-xxx` 번호 이어 쓰기*: 루트 `CLAUDE.md` §1 위반이고, 197개 원장의 카운트와 추적성 게이트가 깨진다.
- *공용 `@shared/domain` 패키지*: LINKOS 의 "추정" 함수와 PROPLUS 의 "추정 금지" 게이트가 한 패키지에 공존하면 둘 다 약해진다(전략 §1-2).

## ADR-010 페이지 빌더는 GrapesJS 가 아니라 블록 schema allowlist 자체 구현이다

**상태** 채택 (2026-10-22)

**맥락**
M03 미니사이트는 사용자가 블록을 배치해 공개 프로필을 구성하는 기능이다. GrapesJS 는 이 범주의 대표 오픈소스지만,
**임의 HTML/CSS/JS 를 저장·렌더하는 것을 전제**한다. 모듈명세 M03 과 전략 §2 N-10 은 그 반대를 요구한다:
미니사이트에 사용자 JS 금지.

**결정**
블록 **모델만 차용**하고 에디터는 직접 만든다.
`packages/domain/src/blockSchema.ts` 가 kind 별 허용 props 키를 화이트리스트로 검사하고,
허용 밖 키는 **에러가 아니라 삭제**한다. 문자열 값은 `sanitizeText()` 를 통과시키고
`html` / `script` / `style` / `on*` 키는 거부한다. 저장되는 것은 검사를 통과한 `jsonb` 블록 배열이며,
**임의 HTML 문자열을 담는 컬럼이 스키마에 존재하지 않는다.** 응답 헤더의 CSP 가 마지막 겹이다.

**근거**
- 모듈명세 M03, 전략 §2 N-10, §6 기술 선택표(Builder).
- 보안정책 §2 "프로필 XSS → `domain/blockSchema.ts` allowlist + `sanitizeText()` + CSP".
- 오픈소스검토 §4 미완(ADR-006) — 지금 GrapesJS 를 도입할 수 없는 별도의 이유이기도 하다.

**결과**
- 표현력이 제한된다. 사용자는 9종 블록(`intro` `badges` `specialties` `offers` `faq` `contact` `links` `metrics` `career`)과
  그 props 안에서만 꾸밀 수 있다. 블록 추가는 schema 수정 + 렌더러 추가가 함께 가는 작업이다.
- 서버 렌더가 가능해져 공개 프로필 LCP 가 가벼워진다(브랜드 §7 접근성·성능).
- "허용 밖 키는 삭제"를 고른 이유: 에디터 버전 차이나 새 필드 실험이 **저장 실패가 아니라 무시**로 끝나야
  사용자 콘텐츠가 사라지지 않는다. 거부해야 하는 것은 위험한 키(`html`/`script`/`style`/`on*`)뿐이다.
- 블록 데이터가 그대로 공개 DTO 로 가지 않는다 — allowlist(ADR-002)를 한 번 더 통과한다.

**대안과 기각 이유**
- *GrapesJS 도입 후 출력 sanitize*: sanitizer 를 뚫는 것이 공격의 본업이고, 저장된 HTML 은 영구 XSS 가 된다. 신뢰를 파는 제품에서 받을 수 없는 위험이다.
- *마크다운 허용*: 링크·이미지·raw HTML 통로가 다시 생기고, 블록별 구조화 데이터(배지·지표·FAQ)를 표현할 수 없다.
- *템플릿만 제공(편집 불가)*: N-10 은 지키지만 M03 요구(사용자가 구성)를 만족하지 못한다.

## ADR-011 CSP 는 nonce 대신 `'unsafe-inline'` 을 쓰고, N-10 방어를 코드 쪽으로 옮긴다

**상태** 채택 (2026-10-24) — Next 가 nonce 를 고치면 되돌린다

**맥락**

N-10(미니사이트에 사용자 JS 금지)의 마지막 겹으로 엄격한 CSP 를 두려 했다.
설계는 표준적이었다: 요청마다 nonce 를 발급하는 미들웨어 + `script-src 'self' 'nonce-…' 'strict-dynamic'`.

**Next 16.4 에서 동작하지 않는다.** 측정한 사실:

- `proxy.ts`(구 `middleware.ts`)가 요청 헤더에 CSP 를 심어도, **클라이언트가 직접 CSP 헤더를 보내도**
  결과가 같다. RSC 페이로드에 `"nonce":"$undefined"` 가 찍히고 `<script>` 에 nonce 속성이 붙지 않는다.
- Next 내부에는 추출기(`getScriptNonceFromHeader`)와 호출부(`parseRequestHeaders`)가 **있는데**
  그 값이 렌더 컨텍스트까지 오지 않는다.
- 그 상태에서 `'strict-dynamic'` 을 두면 브라우저가 `'self'` 를 **무시**하므로
  인라인 스크립트는 물론 `/_next/static/chunks/*.js` 까지 전부 차단된다.

실패 양상이 특히 나쁘다. 서버는 200 을 주고 SSR 마크업도 정상이라 **빌드·타입체크·SSR 스모크가 전부 통과한다.**
깨지는 것은 브라우저의 하이드레이션뿐이고, 사람이 버튼을 눌러 봐야 안다.

**결정**

1. `script-src 'self' 'unsafe-inline'` 를 쓴다. `'unsafe-eval'` 은 **프로덕션에서 제외**한다(dev 만 HMR 용).
2. CSP 는 `next.config.ts` **한 곳**에서만 내려보낸다. `proxy.ts` 는 제거했다.
3. N-10 의 실질적 방어선을 **코드 쪽에 못 박고 테스트로 강제**한다.

**근거**

CSP 는 원래도 N-10 의 *마지막* 겹이었다. 실제로 사용자 입력이 실행되는 것을 막는 것은 아래 넷이고,
전부 테스트가 있다 — 즉 CSP 를 한 단계 양보해도 1차 방어선은 그대로다.

| 방어 | 위치 | 테스트 |
|---|---|---|
| 임의 HTML 을 **저장할 경로가 없다** | `domain/blockSchema.ts` allowlist | `blockSchema.test.ts` (34) |
| 태그·`javascript:`·다중 인코딩 제거 | `domain/sanitize.ts` | `sanitize.test.ts` (28) |
| React 자동 이스케이프 | 프레임워크 | — |
| `dangerouslySetInnerHTML`·`eval`·`new Function` 부재 | 저장소 전체 | `architecture.test.ts` |

마지막 줄이 이 ADR 이 추가한 통제다. 소스를 훑어 기계적으로 막으므로, 누가 우회 수단을 들여오면
PR 에서 실패한다. `object-src 'none'`·`base-uri 'self'`·`form-action 'self'`·`frame-ancestors 'none'` 도 그대로 유효하다.

**결과**

- 인라인 스크립트가 허용된다. 공격자가 **마크업을 주입할 수 있다면** 실행된다 —
  그러나 그러려면 위 네 겹을 먼저 뚫어야 한다.
- `'unsafe-eval'` 이 없으므로 eval 기반 페이로드는 계속 막힌다.
- 모든 화면이 `force-dynamic` 이다(ADR 과 별개로 N-9 가 요구하는 것이기도 하다).
  `scripts/check-no-prerender.mjs` 가 CI 에서 지킨다.

**되돌리는 방법**

Next 가 nonce 를 고치면: `next.config.ts` 의 `script-src` 를 `'nonce-…' 'strict-dynamic'` 으로 바꾸고
요청마다 nonce 를 발급하는 `proxy.ts` 를 되살린 뒤, **실제로 `<script>` 에 붙는지 응답 HTML 로 확인**한다.
헤더에 nonce 가 보이는 것만으로는 동작 증거가 아니다 — 이 ADR 이 그 함정에서 나왔다.

**대안과 기각 이유**

- *`'strict-dynamic'` 유지*: 앱이 통째로 동작하지 않는다. 작동하지 않는 보안 설정은 보안이 아니다.
- *Next 인라인 스크립트의 해시를 CSP 에 넣기*: RSC 페이로드가 요청마다 달라 해시가 고정되지 않는다.
