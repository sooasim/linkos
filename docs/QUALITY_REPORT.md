## 3. 시나리오·시뮬레이션으로 발견해 고친 버그

| # | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | 랜딩을 열지 않고 회신하면(API·네이티브·미리보기 경합) `invalid_state` 409 | 상태머신이 CHANNEL_SELECTED → EXCHANGED 전이를 허용하지 않음 | 회신 시 RECEIVER_OPENED를 먼저 거치도록 수정 + 통합 테스트 |
| 2 | **동시 회신 10건에서 서버 전체가 멈춤(교착)** | 행 잠금을 쥔 트랜잭션이 커넥션 풀에서 두 번째 커넥션을 요청 → 풀 고갈 | 트랜잭션 커넥션 재사용, 풀 연결 5초·statement 15초·lock 10초 타임아웃 추가, 전체 트랜잭션 코드 감사 |
| 3 | 한글 slug 공개 프로필 404 | 동적 경로 파라미터가 퍼센트 인코딩 상태로 전달 | 디코딩 처리 |
| 4 | 연락처 5,000건 대량 유입 직후 목록 p95 11.6초·타임아웃 | 통계가 낡으면 플래너가 1,400만 행 Nested Loop 선택 | 고유 인덱스 상관 조회로 재작성 (4.7초 → 11ms) |
| 5 | AI 관계 검색 p95 20초·오류 176건 | 다중 LEFT JOIN + GROUP BY가 같은 이유로 붕괴 | 소유자 인덱스 단순 쿼리 4개 + 메모리 조인, 부분문자열 사전필터 |
| 6 | 매칭 p95 3.0초 | 후보마다 프로필 조회(N+1, 약 1,500 쿼리) | 3개 배치 쿼리로 변경 |

## 4. 부하 시뮬레이션 (`pnpm loadtest`, 백서 20 SLO)

조건: 연락처 5,000·만남 5,000·메모 약 1,500·연결된 LINKOS 사용자 300명, 동시 20, 시나리오당 200요청, 단일 Node 프로세스 + PostgreSQL 16 (클라우드 컨테이너).

| 시나리오 | p50 | p95 | SLO(p95) | 결과 |
|---|---|---|---|---|
| 교환 세션 생성 | 59ms | 82ms | 300ms | PASS |
| 게스트 랜딩 API | 59ms | 75ms | 300ms | PASS |
| 게스트 랜딩 SSR `/x/{token}` | 124ms | 159ms | 800ms | PASS |
| 연락처 목록 | 114ms | 152ms | 400ms | PASS |
| 연락처 검색 | 124ms | 159ms | 400ms | PASS |
| AI 관계 검색 | 1044ms | 1322ms | 1500ms | PASS (여유 적음) |
| Need↔Offer 매칭 | 216ms | 255ms | 1500ms | PASS |
| 홈 SSR | 289ms | 380ms | 1000ms | PASS |

통계가 낡은 최악 조건(autovacuum 중지)에서도 8개 모두 통과. AI 검색은 연락처 수에 비례하므로, 수만 건 규모에서는 pg_trgm/FTS 인덱스 또는 임베딩 검색으로 바꿔야 한다.

## 5. Google Sheets / Google 연동

- 구현: OAuth(서명된 state, 최소 권한 `drive.file`), 새 스프레드시트 생성 후 선택 필드를 `RAW`로 기록(수식 실행 방지), People API 연락처 생성·etag 갱신, 계정별 직렬 처리, 지수 백오프 재시도, 토큰 자동 갱신, 재인증 상태 표시.
- 검증: 실제 API와 같은 형태의 가짜 Google 서버로 통합 테스트 6개 통과.
- **미검증**: 실제 Google 계정 연결. 이 환경에는 OAuth 클라이언트가 없다. `GOOGLE_CLIENT_ID/SECRET` 설정 후 실계정 1회 검증이 필요하다(절차: RUNBOOK "Google 연동 설정").
