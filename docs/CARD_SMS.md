# X-009 문자명함 전송 — 설계와 CardBridge MVP 비교

종이 명함만 받은 상대에게, 그 명함에서 읽은 번호로 내 명함(이미지 + 기본정보 + 저장 링크)을 문자로 보내는 기능이다.
구현: `packages/domain/src/cardSms.ts`(순수) · `services/api/src/modules/cardSms.ts` · `services/api/src/lib/{sms,ocr}.ts` ·
`apps/web/src/app/app/card-sms/*`(보내는 화면) · `apps/web/src/app/s/[token]/*`(받는 화면).

## 1. 왜 이 모양인가

- **받는 사람은 비회원이다.** 랜딩은 로그인·앱설치를 요구하지 않고, 첫 화면의 가장 큰 버튼이 "연락처에 저장"이다(§2.1).
- **구글 연락처에 자동으로 써 넣는 링크는 없다.** 그건 수신자의 OAuth 동의가 필요한 People API 호출이다.
  그래서 보편적으로 동작하는 `.vcf` 한 장(안드로이드/구글 연락처·iOS 연락처가 모두 "연락처 추가" 화면을 띄운다)과
  컴퓨터용 가져오기 안내만 제공한다. 할 수 없는 일을 할 수 있는 척 하지 않는다(§2.4의 태도).
- **발송은 사용자가 누를 때 1건씩**(§2.8). 자동·예약·대량 발송 경로는 만들지 않았다.
- **어떤 상태도 "상대가 받았다"가 아니다.** `sent`=외부 접수, `uncertain`=응답 없음, `manual`=문자 앱으로 넘김.

## 2. 보낼 수 있는 세 가지 길

| 경로 | 받는 사람에게 보이는 발신번호 | 요금 | 이미지(MMS) | 전제 |
|---|---|---|---|---|
| `gateway` 내 안드로이드 SIM | **내 번호** | 내 요금제 | 불가(본문만) | 사용자가 공식 [Android SMS Gateway](https://github.com/capcom6/android-sms-gateway) 앱 설치 + Cloud 인증정보 연결 |
| `provider` 상용 API(Solapi·Twilio) | 사전등록 서비스 번호 | 건당 과금 | 가능 | 서버 env + 발신번호 사전등록 |
| `device` 내 문자 앱 | 내 번호 | 내 요금제 | 불가 | 없음 — 항상 쓸 수 있는 폴백 |

기본값은 `gateway` → `provider` → `device` 순이다. 명함을 건넨 상대에게는 모르는 서비스 번호가 아니라 **본인 번호**가 맞다.
게이트웨이 엔드포인트는 서버에 고정돼 있어 사용자가 URL 을 고를 수 없다(SSRF 경로를 만들지 않는다). Local/Private 서버
모드는 임의 주소로 POST 하는 길을 열어야 하므로 허용 목록·사설망 차단 설계 없이는 지원하지 않는다.

## 3. CardBridge MVP(`dd/CardBridge_AI_/cardbridge-source`)와의 비교

같은 문제를 푸는 FastAPI + SQLite 단일 서비스 MVP다. 코드를 복사하지 않고, 설계 판단과 운영 교훈만 비교해 반영했다.

### 3.1 CardBridge 가 더 낫던 점 → 가져온 것

| 항목 | CardBridge | 반영 결과 |
|---|---|---|
| **사용자 SIM 직접 발송** | Android Gateway Cloud API 연동 | 그대로 채택. 사용자별 인증정보는 기존 vault 로 봉인(`sms_gateway_accounts`, 키 교체 대상), 엔드포인트 고정, 저장 시 1회 연결 확인 |
| **접수 불확실 상태** | `uncertain` — 네트워크 실패 후 재시도하지 않음 | `SmsUncertainError` → `status='uncertain'`. 자동 재시도 없음. 같은 건을 다시 눌러도 외부 호출이 늘지 않는다 |
| **사람 기준 남용 방지** | 30초 간격 · 하루 20건 · 동일 번호 24시간 중복 차단 | `domain.sendGuard()`(순수, 단위테스트) + `destination_hash` 로 판정. 시간당 rate limit 과는 별개 층 |
| **이력의 PII 최소화** | 번호 전체를 기록하지 않고 HMAC + 마스킹 | 목록 응답에서 전체 번호·본문·딥링크를 빼고 `010-****-1234` 만 내보낸다. 중복 판정은 `hmac()` 해시로 |
| **본문 자동입력 실패 대비** | 플랫폼별 `?`/`&` 구분자 + 본문·번호 복사 버튼 | `smsDeepLink(phone, body, platform)` + UA 기반 `smsPlatform()`, 완료 화면에 복사 버튼 2개, 데스크톱 경고 |
| **서버 OCR 폴백** | Google Vision DOCUMENT_TEXT_DETECTION 우선, Tesseract 폴백 | 순서를 뒤집어 채택: 기본은 기기 내 OCR(사진이 안 나간다), **번호를 못 읽었을 때만** 사용자 동의를 받아 Vision 으로 재시도 |
| **고지 문구** | 모든 응답에 "접수는 발송이 아니다" | 완료 화면·상태 라벨·목록에 상태별 문구로 반영 |

### 3.2 이 저장소가 이미 더 나았던 점 → 유지

| 항목 | CardBridge | X-009 |
|---|---|---|
| 촬영 전처리 | 업로드 이미지를 그대로 OCR | 테두리 검출 → 원근 보정 → 대비 보정 후 OCR(`domain/imaging.ts`) |
| 사진 처리 위치 | 서버 업로드 후 OCR | 기본은 기기 내(사진이 서버에 올라가지 않는다) |
| 구조화 | 정규식 휴리스틱(이름은 한글 2~4자 등) | 필드별 신뢰도·bbox·provenance 를 남기는 결정적 파서 + 저신뢰 필드 검토 UI |
| 수신 번호 | 국내 010 11자리만 | 41개국 E.164 정규화. 국내 유선번호는 **차단 대신 경고** |
| 보내는 명함 | 사용자가 올린 사진 1장 | Living Card 를 캔버스로 렌더한 PNG(템플릿 50종의 토큰 색) + 필드 ACL 투영 |
| 받는 화면 | 정적 HTML + .vcf | LivingCard(3초/30초/딥) + 저장·전화·메일·복사 + 열람/저장 추적 |
| 링크 토큰 | `secrets.token_urlsafe(18)` 공개 id, 만료 없음 | 192bit, DB 에는 SHA-256 해시만 + 재공유용 봉인 사본, 30일 TTL, 취소 가능 |
| 저장 데이터 | SQLite 단일 파일 | Postgres + 감사로그(해시 체인) + outbox + 보존 정책(만료 링크의 이미지 자동 삭제) |

### 3.3 가져오지 않은 것과 이유

- **Google People API 로 상대 주소록에 직접 쓰기** — CardBridge 도 하지 않는다(수신자 OAuth 필요). `.vcf` 가 정답이다.
- **Gateway Local/Private 서버 모드** — 임의 URL POST 를 허용해야 해서 SSRF 방어 설계가 선행되어야 한다.
- **MMS(그림문자) 게이트웨이 발송** — 공식 문서가 기본 SMS 앱 역할 등 추가 조건을 요구한다. 그 경로에서는 본문만 보내고,
  명함 이미지는 링크를 열면 보인다.
- **대량 발송·주소록 일괄 전송** — 기능으로 만들지 않는다(§2.8, 정보통신망법).

## 4. 남아 있는 제약 (운영 전 확인)

- 통신사 발송·도착 보장은 어느 경로에도 없다. 배달 확인이 필요하면 provider/게이트웨이의 공식 웹훅 + 서명 검증을 별도 설계해야 한다.
- 화면에서 체크한 "상대가 명함을 직접 건넸다"는 보낸 사람의 확인이며(행에 `consent_basis='card_handed'` 로 남는다),
  그 자체가 법적 동의 증거는 아니다. 광고성 문자에 해당하는 사용이라면 정보통신망법상 별도 요건이 적용된다.
- 서버 OCR 을 켜면 이미지가 Google 로 전송된다 — 개인정보 처리방침·국외이전 고지를 먼저 갱신해야 한다.
- 실기기 회귀시험(iOS Safari/Chrome, Android Chrome/삼성인터넷, 듀얼 SIM, 본문 자동입력 여부)은 자동 테스트로 덮을 수 없다.
